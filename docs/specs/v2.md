# Reflekt v2 — Specification

**Status:** Scoped, ready for implementation
**Owner:** Laurentiu
**Depends on:** Reflekt v1 deployed and functional
**Related:** `reflekt-v1-SPEC.md`, `agentic-rituals-suite-strategy.md`

---

## 1. Purpose & Scope

V2 makes Reflekt usable beyond a single-team pilot and fills UX gaps exposed by competitor analysis. All features are non-AI — agent-authored cards, memory layer, Jira API integration, and cross-sprint analytics are explicitly deferred to v3.

V2 also positions Reflekt for external users to try it (guest + Google dual-path auth), which means the app must handle multiple teams cleanly and not rely on a single hardcoded team.

**V2 is NOT:**
- AI-powered anything. No agent cards, no memory layer, no semantic search.
- A product launch. Still internal tooling + course demo material.
- A rewrite. V2 builds on v1's data model, extends it.

## 3. Feature Specifications

### 3.1 Google Auth for Participants (Dual Path)

**Problem:** V1 has Google-authed team creator (SM) and ephemeral guest participants (localStorage token, display name only). Guests have no persistent identity — they can't be recognized across sprints or devices. External users trying the app lose all history on browser clear.

**Decision:** Support both paths. Don't force Google login — it adds friction for casual users and kills the "try it in 30 seconds" flow.

**Two participant identity tiers:**

- **Google-authed participant:** Signs in with Google before joining a sprint. Gets a persistent `User` record (same entity the SM uses). Recognized across sprints, across devices, across teams. Display name and email pulled from Google profile.
- **Guest participant:** Same as v1. Picks a display name, gets a localStorage token, sprint-scoped. No persistence beyond the browser session.

**Data model impact:**

- `Participant` table gains an optional `UserId` FK → `User`. Null for guests, populated for Google-authed participants.
- A Google-authed user joining a sprint creates a `Participant` row linked to their `User` record. If they join the same sprint from another device, they get a second `Participant` row linked to the same `User` — same as v1's "rejoin" behavior but now identity-aware.
- The `User` table already exists (team creator). No new table needed.

**UX flow:**

1. Participant opens the sprint join link.
2. Landing page shows two options: "Join with Google" (button) or "Join as Guest" (name input + join button).
3. Google path: OAuth flow → redirected back to sprint → auto-joined with Google profile name.
4. Guest path: enter display name → join → same as v1.

**What this enables for v3:** Cross-sprint history per user, action item ownership that persists, user-level analytics.

**Why both paths:** Laurentiu's team will use Google. External users trying the app for the first time should not be forced through OAuth. The guest path is the low-friction entry point; Google is the upgrade path.

### 3.2 Multi-Team Support

**Problem:** V1 is hardcoded to a single team. Laurentiu manages multiple sub-teams. External users trying the app also need their own teams.

**Decision:** Up to 10 teams per Google-authed user. The limit is a soft guard against abuse, not a technical constraint. Stored in config, adjustable.

**Rules:**
- Any Google-authed user can create a team. They become the SM for that team.
- One user can create up to 10 teams (configurable via `appsettings.json`).
- Team names must be unique per user (not globally).
- The SM dashboard (post-login landing page) shows all teams the user owns, with sprint counts and last-activity timestamps.

**Data model impact:** No schema change — `Team` already has `CreatedByUserId`. The limit is enforced at the API level on team creation.

**UX flow:**
- After Google login, SM sees a team list (cards or table). Each team shows: name, number of sprints, last sprint date.
- "Create Team" button, gated to the 10-team limit.
- Clicking a team navigates to its sprint list (existing sprint manager page, scoped to that team).

### 3.3 Team Deletion with Cascade

**Problem:** If users can create up to 10 teams, they need to be able to delete teams to recycle slots. Deletion must be clean — no orphaned sprints, participants, cards, votes, or evidence links.

**Decision:** Hard delete with full cascade. No soft delete — this is a lightweight tool, not an enterprise audit trail.

**Cascade order:** Team → Sprints → Participants → Cards → Votes + EvidenceLinks → CardGroups. All in a single transaction.

**UX flow:**
- Team card/row in the SM dashboard has a delete action (icon or menu).
- Confirmation dialog: "Delete team '{name}' and all its sprints? This cannot be undone."
- Must type the team name to confirm (prevents accidental clicks).
- Only the team creator (SM) can delete their own teams.

**Guardrail:** Cannot delete a team that has an active (non-closed) sprint. Close or delete the sprint first. This prevents deleting a team mid-retro while participants are connected.

### 3.4 Inline Phase Controls

**Problem:** In v1, the SM must navigate back to the sprint manager page to advance the phase (Writing → Voting → Discussing → Closed). This breaks flow during a live retro.

**Decision:** Move phase controls into the sprint board view. The separate page navigation for phase advancement is removed.

**Every major competitor (Parabol, TeamRetro, EasyRetro, Reetro) puts phase controls inline on the board.** Nobody uses a separate admin page.

**UX:**
- Top bar on the sprint board shows: current phase name + "Next: {phase}" button (right-aligned).
- Visible to all participants (so everyone knows what phase they're in). Actionable only by the SM.
- Non-SM participants see the phase indicator but no button.
- Phase transitions are pushed via SignalR to all participants in real-time (already exists from v1).
- The "Close Sprint" action (final phase transition) shows a confirmation: "Close this sprint? No more changes will be allowed."

**What stays on the sprint manager page:** Sprint creation, sprint list, sprint settings (name, date). Phase advancement moves out.

---

### 3.5 Open Actions from Previous Retro

**Problem:** Retros should start by reviewing what was committed last time. Currently there's no connection between sprints — each retro starts from zero.

**Decision:** At the start of a new sprint's retro (Writing phase), show action items from the most recent closed sprint in the same team. The SM can mark each as Done, Carried Over, or Dropped.

**Rules:**
- Only action items (cards with `CardType = ActionItem`) from the previous closed sprint are shown.
- "Previous sprint" = the most recently closed sprint in the same team, by `ClosedAt` timestamp.
- If there's no previous sprint (first retro), this section doesn't appear.
- The review happens inline at the top of the sprint board during the Writing phase — not a separate step or phase.
- Status updates (Done / Carried Over / Dropped) are persisted on the original action item card in the previous sprint, not copied into the new sprint.

**Data model impact:**
- `Card` table gains a `ReviewStatus` enum column: `None` (default), `Done`, `CarriedOver`, `Dropped`. Only meaningful for `CardType = ActionItem`.
- `Card` table gains a `ReviewedInSprintId` nullable FK — which sprint reviewed this action item. Enables cross-sprint traceability without duplicating cards.

**UX:**
- Collapsible section at the top of the sprint board: "Actions from last sprint ({count})".
- Each action item shows: text, assignee, and three buttons (Done ✓ / Carried Over → / Dropped ✗).
- SM-only interaction. Participants can see the section but not change statuses.
- Once all items are reviewed, the section collapses and stays collapsed. Can be re-expanded.

**Why not copy actions into the new sprint:** Duplication creates data integrity issues. The action lives in its original sprint; the new sprint merely references and reviews it.

### 3.6 Timer per Phase

**Problem:** Retros run long. Every competitor has per-phase timers. Without them, the SM has to use a phone timer or just wing it.

**Decision:** Optional countdown timer per phase, controlled by the SM.

**Rules:**
- The SM can start a timer at any point during a phase. Not required — phases can run untimed.
- Timer is visible to all participants in real-time (SignalR broadcast).
- When the timer hits zero: visual + optional audio alert. The phase does NOT auto-advance — the SM decides when to move on.
- The SM can: start, pause, reset, or add time (+1 min, +2 min, +5 min).
- Default durations (configurable per sprint at creation, stored in `Sprint` settings):
  - Writing: 5 minutes
  - Voting: 3 minutes
  - Discussing: 10 minutes

**Data model impact:** Minimal. Timer state is ephemeral — managed in memory on the server (or via SignalR group state). No persistence needed. Default durations are stored as a JSON column on `Sprint` (`TimerDefaults`).

**UX:**
- Timer appears in the top bar next to the phase controls (§3.4).
- Compact display: `03:42` countdown. SM sees start/pause/reset/+time controls. Participants see the countdown only.
- Timer expiry: the countdown flashes red, optional browser notification sound (respect mute preference).

### 3.7 Configurable Reflection Columns

**Problem:** V1 has three hardcoded columns: Went Well / Didn't Go Well / Action Items. The "Start Doing" concept (new ideas, practices from other teams) has no home. Different retro formats use different column names.

**Decision:** 3 configurable reflection columns + 1 fixed Action Items column. The SM sets the reflection column names at sprint creation. Action Items is always present and structurally separate (has assignee field, no voting).

**Clarification on the model:**

Reflection columns are for observations — what the team noticed. Action Items are for commitments — what the team will do. "Start doing" is an observation ("we should try X"), not a commitment. It belongs in a reflection column. If the team decides to act on it, someone creates an action item.

**Rules:**
- Default column template: "Good" / "Bad" / "Start Doing" + Action Items.
- The SM can rename any of the three reflection columns at sprint creation. Free-text names, max 30 characters.
- Column order is fixed as entered (left to right = column 1, 2, 3, then Action Items rightmost).
- Columns cannot be added or removed beyond the 3+1 structure. This keeps the UI predictable and avoids the "template engine" rabbit hole.
- Column names are stored per sprint, not per team. Different sprints in the same team can use different column names.

**Data model impact:**
- `Sprint` table gains: `Column1Name`, `Column2Name`, `Column3Name` (string, max 30, with defaults "Good", "Bad", "Start Doing").
- `Card.ColumnType` enum changes from `WentWell / DidntGoWell / ActionItem` to `Column1 / Column2 / Column3 / ActionItem`. The semantic meaning is defined by the sprint's column names, not the enum value.

**UX:**
- Sprint creation form includes three text inputs for column names, pre-filled with defaults.
- On the sprint board, column headers display the custom names.
- Action Items column header is always "Action Items" — not editable.

**Common mappings (for reference, not enforced):**

| Template | Column 1 | Column 2 | Column 3 |
|----------|----------|----------|----------|
| Default | Good | Bad | Start Doing |
| Classic | Keep Doing | Stop Doing | Start Doing |
| Emotional | Glad | Sad | Mad |
| 3L | Liked | Lacked | Learned |

## 4. What's Explicitly NOT in V2

- **Agent-authored cards** → v3. Requires memory layer.
- **Memory layer / context store** → v3. Separate service, significant investment.
- **Jira API integration** → v3. Evidence links remain URL-based with OpenGraph fetch.
- **Cross-sprint analytics** → v3. Trend detection, recurring themes, estimate-vs-actual correlation.
- **Card comments / discussion threads** → maybe v3. Not essential for a 5-15 person retro where discussion happens live.
- **Icebreaker questions** → not planned. Low value for the target team.
- **Emoji reactions / kudos** → not planned. Nice-to-have, not a gap.
- **Card masking (hide-then-reveal)** → not planned. V1's blurred-card approach during writing is sufficient. Cards are already anonymous and unreadable during the writing phase.
- **Custom retro templates (beyond column names)** → not planned. Column naming covers 90% of the need without building a template engine.
- **Presentation mode** → not planned. The SM drives discussion verbally during the Discussing phase.

## 6. Implementation Sequencing

Features should be built in dependency order, not epic-complete. Recommended order:

1. **Configurable reflection columns (3.7)** — Schema change on `Sprint` and `Card`. Touches the core data model. Do first to avoid rework.
2. **Multi-team support (3.2)** — API-level team limit enforcement + SM dashboard showing team list. Low risk, enables testing with multiple teams.
3. **Team deletion with cascade (3.3)** — Depends on multi-team being testable. Straightforward cascade delete.
4. **Google auth for participants (3.1)** — Extends the existing OAuth flow. `Participant` table gets `UserId` FK. Join page gets dual-path UI.
5. **Inline phase controls (3.4)** — Frontend-heavy. Move the phase advance button into the sprint board. Remove the navigation-back flow.
6. **Timer per phase (3.6)** — Builds on inline phase controls (same top bar). SignalR broadcast of timer state.
7. **Open actions from previous retro (3.5)** — Last because it depends on having at least one closed sprint with action items to reference. Needs the `ReviewStatus` column and cross-sprint query.

## 7. Decision Log

| Decision | Reasoning |
|----------|-----------|
| Both Google + Guest participant paths | Reduce friction for external users trying the app. Google is the upgrade path for persistent identity. Guest is the 30-second onboarding. |
| Hard delete on team deletion, not soft delete | Lightweight tool, not enterprise. No audit trail requirement. Soft delete adds query complexity everywhere for no benefit. |
| Type-to-confirm on team delete | Prevents accidental deletion. Standard UX pattern for destructive actions. |
| Cannot delete team with active sprint | Prevents data loss mid-retro. Close the sprint first. |
| Phase controls inline, not separate page | Every competitor does this. The separate page was a v1 shortcut that created SM friction. |
| Timer does not auto-advance phases | The SM decides when to move on. Auto-advance would cut off participants mid-thought. Timer expiry is a signal, not a gate. |
| 3 configurable + 1 fixed Action Items | Covers the common retro formats (Stop/Start/Continue, Good/Bad/StartDoing, Mad/Sad/Glad) without building a template engine. Action Items is structurally different (assignee, no voting) so it stays fixed. |
| Column names stored per sprint, not per team | Different retros may use different formats. Per-sprint gives maximum flexibility with zero extra complexity. |
| Review actions from previous sprint, not copy them | Copying creates duplication and data integrity issues. The action lives in its original sprint; the new sprint references it. |
| Timer state is ephemeral (not persisted) | Timer is a live facilitation tool. There's no value in persisting "the timer was at 2:34 when the SM paused it." Default durations are persisted on Sprint for convenience. |
| ColumnType enum uses positional values (Column1/2/3) not semantic | Semantic values (WentWell, DidntGoWell) break when columns are renamed. Positional values are stable regardless of display names. |
