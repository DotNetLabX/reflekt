# F39-FrontendConventions — Lessons

## Architect Lessons

- **Compare the campaign's build order with the spec's Dependencies at Phase 1.** F39's spec depends on F38 (the new error body), but the campaign builds F39 on F36 only, so this tree still carries the pre-F38 error body and three SPA consumers parse it. A plan written to the spec's order alone would have shipped generic error text into `main` whenever F39 merges before F38. At Phase 1 of any campaign unit, read `campaign.json` `buildsOn` beside the spec's Dependencies and plan for the tree as built, not as ordered in the backlog.
- **Adding lint while the package files are frozen: prove the install path and mind `tsconfig.node.json`.** `npm install --no-save <pkgs>` left `package.json` and `package-lock.json` byte-identical (run at plan time), so configs can be committed and lint run before a change note adds the dev-dependencies. The Vue scaffold's `tsconfig.node.json` includes `eslint.config.*`: a TypeScript `eslint.config.ts` would break `vue-tsc --build` in every tree where the lint packages are not installed (any `npm ci` run), so the config has to be `eslint.config.js` until the dependencies land.
- **A semicolon-free Prettier reformat breaks Vue's multi-statement inline handlers. Grep for them before writing "no hand edit" into a reformat step.** Vue's template compiler treats a handler as several statements only when it contains a `;`. With `semi: false`, Prettier split `@click="a = x; b.add(y)"` onto two lines with no `;`, and Vue's compiler rejected it as a single expression, so the build broke. That left F39 Step 1's "no hand edit to `src`" Accept unsatisfiable. When a plan's reformat drops semicolons in a Vue SPA, first run `grep -rnE '@[a-z.:-]+="[^"]*;' src --include=*.vue` and plan the handler extraction into that step. [F39-FrontendConventions]
- **A `prettier --check` gate in a repo with `core.autocrlf=true` needs `endOfLine: "auto"`.** Windows checkouts write CRLF working files, so Prettier's default `lf` fails the check on every file in any fresh checkout, though it passes in the tree that ran the `--write`. Read `git config core.autocrlf` when planning a format gate. [F39-FrontendConventions]

## Developer Lessons

- **A frontend-only feature's step close does not test the frontend here.** `.claude/verify.json` `roles.unit` is the .NET unit project only, so `verify-run.js --profile fast --tied --changed {web files}` cannot tie anything and falls back to the whole backend unit run; the SPA's real per-step check is the plan-named `npm --prefix web/reflekt-web run type-check` (and `run build`), run beside the tied close. A repo with an SPA and no frontend tests would benefit from a declared frontend check (e.g. a `typecheck` role) the step close can address, so the record names what was actually verified.
- **A probe script in `.claude/tmp/` cannot `import 'vite'`.** Node resolves bare imports from the script's own folder, and `.claude/tmp/` has no `node_modules`, so `import { createServer } from 'vite'` fails with `ERR_MODULE_NOT_FOUND`. On Windows a raw `D:\…` path also fails (`ERR_UNSUPPORTED_ESM_URL_SCHEME`). What works, run from `web/reflekt-web`: `const { createServer } = await import(pathToFileURL(process.cwd() + '/node_modules/vite/dist/node/index.js').href)`, then `createServer({ configFile: './vite.config.ts', server: { middlewareMode: true }, optimizeDeps: { noDiscovery: true } })` and `ssrLoadModule('/src/…')` (it resolves `@/`). Plan Step 11's markdown-equality script uses the same mechanism.
- **Moving a store onto `apiFetch` collapses two error paths into one `catch`.** Before, a non-OK reply and a failed `fetch` were separate branches with different texts ("Failed to load …" and "Can't reach the server"). Now both reject, and so does an unreadable body. Branch on `ApiError.status !== 0` (`isHttpError` in `src/api/client.ts`) to keep both texts. `describeApiError` on its own shows the fallback for a network failure, so a load that showed "Can't reach the server" needs that guard in front of it. Also note that setup stores have no `$reset`; check for `$reset`/`$patch` callers before converting an options store.

- **A git command that "only touches the index" is still a git write.** In Step 9 (steps 8–11 build) I ran `git rm --cached` while deleting a merged component and staged a deletion under a no-git-writes rule; the coordinator had to unstage it. Delete and move files with plain `rm`/`mv` only — never `git rm`, `git mv`, `git add`, `git restore`, even for a file the step deletes anyway. [F39-FrontendConventions]
- **A line cap on a view (`< 100`) pushes markup into small single-use components.** Here it took two that the plan did not name (`RetroRoomBanners`, `RetroKickedNotice`), plus moving one-line computeds into the room composable. When a plan sets a hard line cap, it should list the extractions it expects, or accept "markup-only extractions are the developer's call". [F39-FrontendConventions]
- **A phase-literal grep with only `src/types/`, `src/stores/` and the phase composable exempt moves every phase-specific UI text into that composable.** Here that was the advance dialog's messages (`useRetroPhase.advancePrompt`). Expect it when planning such a grep. [F39-FrontendConventions]
- **Never put Vue template text with backticks inside `node -e "…"` in Git Bash.** Bash runs `` `…` `` as command substitution inside double quotes. Here it emptied `:aria-label` bindings and broke two edits (`text-col-${color}` became a "No such file" error). It also matters that the shell's heredoc can fail on long prose. Write the edit script, or the prose block, to `.claude/tmp/` with the Write tool or a `<<'EOF'` heredoc, then run or append it from there. [F39-FrontendConventions]
- **`dotnet run --no-launch-profile --environment Development` still started this API in Production, and every non-static route answered 400.** Set `ASPNETCORE_ENVIRONMENT=Development` in the environment, and pick a free port with `--urls` (parallel worktrees share 4001). The SQLite file it creates (`Reflekt.API/data/`) is git-ignored; delete it after a smoke run. [F39-FrontendConventions]
- **The `--no-save` lint packages do not survive the handover's complete run.** `roles.full` runs `npm ci`, which removes anything not in the lockfile, so a fix round finds no `prettier`/`eslint` in `node_modules/.bin`. Reinstall with Step 1's exact pinned `--no-save` command before `prettier --check`/`eslint .`, then confirm `git status --porcelain` on both package files is empty. [F39-FrontendConventions]
- **Adopting a Base* component changes every look property it owns, not just the one the plan names.** `BaseCard` brought `rounded-md` to frames that had 4 px and 12 px corners, and the review counted that as an unlisted visible change. When the spec's visible-change list is exhaustive, diff each look property the component sets (radius, padding, shadow) against the old markup, and keep the old value through a prop where the list does not cover it. [F39-FrontendConventions]
- **Applying only part of a reviewer's directed fix costs a round.** Codex asked to honour settlement for both totals and own vote counts; Fix Round 1 honoured it only for totals, on my own reasoning (no broadcast corrects a skipped own count), and the re-review reopened it as a cross-sprint bug. In an optimistic store, a settlement flag set by any snapshot must gate both the confirm and the rollback path. When I disagree with part of a directed fix, I ask through `questions.md` before the hand-back, not record it as a Decision after. [F39-FrontendConventions]

## Team Lead Lessons

- **The handover `npm ci` wipes `--no-save` lint packages.** Every reader and fix developer after the handover run found eslint/prettier gone and either reinstalled them or skipped lint. Until change Note 1 puts the lint devDependencies in `package.json`, name "reinstall the lint packages without saving" in every post-handover dispatch for a frontend unit.
- **A MEDIUM-only fix round closes on the developer's report.** Cycle 2 carried one MEDIUM, so no follow-up review ran; the fix is listed "fixed, not re-verified" in the summary. Recorded so the next unit expects it rather than scheduling a third Codex read.
