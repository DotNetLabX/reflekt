# F38-BackendConventions — Lessons

## Architect Lessons

- **Spec acceptance written as new tests under a "no new tests" campaign.** F38's AC7 (two `code` cases) and AC8 (handler and rollback tests) can only be met by new test cases, while the owner's campaign directive forbids them — the same conflict F35 already had to rule on (F35 `questions.md` Q1). A tech-spec written for a campaign should check each acceptance line against the campaign directives and name, per line, the existing test it updates or the code trace / evidence run that replaces it. Evidence: [F35-BackendCorrectnessFixes, F38-BackendConventions]
- **A detached (fire-and-forget) task must not inherit the request's cancellation token.** F38's plan made event publication detached but kept "the token F35 passes today", which is the endpoint's `ct` from `RequestAborted`; round 1 caught it. When a plan moves work out of the request's lifetime, name the token the detached work uses (`CancellationToken.None` or an app-stopping token) in the step itself — it removes the need to know whether the server signals the request token after a normal completion.
- **Count call sites with the receiver, not the bare method name.** The plan's "18 files that call `IsAllowed(`" swept in the cache's own definition and an unrelated `OpenGraphAddressPolicy.IsAllowed`, and wrongly placed the hub among the callers. Grep `receiver.Method(` and list the files.
- **Moving per-read scopes to constructor injection can silently break a deliberate fresh read.** F38 Step 10 injected the hub's repositories (spec BE-11); F35's `JoinSprint` relied on a second, separately scoped read to catch a kick committed in between, and `FindAsync` on a shared `DbContext` would have answered from the tracker. Before planning a scope consolidation, grep the code for a re-read of the same id in one method and pin it with an `AsNoTracking` query. Read the comments around race fixes too.
- **"Drop the endpoint check where the domain throws the same text" moves a message behind any check in between.** State that rule together with its position condition.
- **Plan accept greps over `src` must scope to source files** (done check, F38): two plan greps written over bare `src` matched files no step can change — EF migration designer files (`HasMaxLength(n)` literals) and the gitignored SPA bundle in `Reflekt.API/wwwroot/assets/` that the complete run's `npm run build` writes (`limit_reached:`). Write accept greps with `--include=*.cs` (as the spec's own AC greps do) and exclude `Migrations/`, so the done check confirms rather than adjudicates.
- **"The only X lives in Y" needs a grep for X in the endpoints the plan exempts from Y** (F38 P4/Step 3 vs Step 5): the plan said the one `OwnerId` comparison lives in `SprintAccess`, while another step kept the anonymous `GetSprintSummary` outside `SprintAccess` with its own comparison. Before writing an exclusivity claim, grep the exempted sites and either name them as the exception or narrow the claim.
- **Fix round 1 (Q2/Q3): "fire-and-forget" in a refactoring spec quietly gave up the order of live updates.** I wrote "event publishing stays fire-and-forget" to keep behaviour change 2 (a failed send does not fail the request). I then turned down "awaiting the publication" as if awaiting meant failing. Those are two separate properties: whether the save waits, and whether a failure propagates. Detaching the task let one request's broadcast be overtaken by a broadcast from a request sent after its response, and Codex caught it as a HIGH. Lesson for planning a dispatch change in a behaviour-neutral refactor: list the ordering guarantees the old code gave across requests (a send awaited before the response is one), not only the guarantees within one request, and keep "waits" separate from "propagates failure" in the Decisions rows. **Evidence:** [F38-BackendConventions]
- **A fix-round plan amendment must name the downstream records it makes stale** (F38 re-check after cycle 1): P7 superseded P5 and Step 4 was redone, but Step 17's AC8 table row and its F40 skill/code list item 3 still described the detached publication task. The amendment listed the plan sections it changed, not the verification records built on the old decision. When an amendment supersedes a decision, grep `implementation.md` (the verification step and the hand-off lists) for the superseded mechanism and name each record to refresh in the fix list or the close.

## Developer Lessons

- **On a FastEndpoints endpoint, a bare `Policies.X` does not compile.** `Endpoint<,>` inherits a `Policies(string[])` method, and a class attribute's arguments see inherited members, so `[Authorize(Policy = Policies.X)]` fails with CS0119 whatever the namespaces are. The `AuthPolicies` alias existed for this reason as well as the `Features.Auth` shadowing; once that namespace is gone, `Auth.Policies.X` is the alias-free form. Before a plan claims that an alias or using can go, compile one file (or a small probe) instead of reasoning about name lookup. Evidence: [F38-BackendConventions]
- **FastEndpoints 5.34.0 cancels sibling event handlers when one fails, in every wait mode.** Each handler gets a linked token that is cancelled as soon as another handler of the same event throws (probed for both `WaitForNone` and `WaitForAll`). A `WaitForAll` task faults with an `AggregateException` holding every handler's failure, while `await` rethrows only the first, so a publisher that logs failures must read `task.Exception.InnerExceptions` (for example, after `ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing)`). A handler that must finish even when a sibling fails should not depend on the token it is given. Evidence: [F38-BackendConventions]
- **An integration failure can be unreadable through the runner.** `verify-run.js --files` cannot target a vstest integration file (it falls back to the unit role), and a red record keeps only a head and tail excerpt, so the exception message of a test that failed at host start-up was cut. One red in three identical runs of F38 Step 1 stayed undiagnosed. When a plan names an integration role, expect to re-run the whole role to tell a flake from a defect. Evidence: [F38-BackendConventions]
- **A SignalR hub with constructor-injected repositories shares one `DbContext` per hub method call, not per connection.** SignalR resolves the hub from a new DI scope for each hub method call and for connect and disconnect. So two reads of the same entity inside one hub method go through one `DbContext`, and `GetByIdAsync` (`FindAsync`) answers the second read from the change tracker without querying. A re-check that must see a write committed in between (F35's kick re-check in `JoinSprint`) needs a no-tracking query (`ParticipantRepository.IsActiveAsync`). A read that comes first in its hub method call queries the database anyway. When moving hub reads from per-read scopes to constructor injection, list every method that reads the same entity twice. Evidence: [F38-BackendConventions]
- **A plan grep scoped to a whole service folder also matches EF's generated migrations.** `Reflekt.Persistence/Migrations/*.Designer.cs` and the model snapshot carry the literal `HasMaxLength(n)` values the configurations had when each migration was generated, and they may never be edited by hand. F38 Step 13's "no literal numbers" grep over `src/Services/Reflekt` therefore cannot come back empty; it does once `Migrations/` is excluded. An accept grep over Persistence source should exclude `Migrations/` (`grep -v /Migrations/`) from the start. Evidence: [F38-BackendConventions]
- **A scratch evidence run can host the API in a console app with the integration helpers, but it needs two fixes.** (1) No top-level statements: the console's own generated `Program` shadows the API's (`CS0436`, only a warning), and `WebApplicationFactory<Program>` then hosts the console instead of the API. Put `Main` in a named class. (2) Set `ASPNETCORE_TEST_CONTENTROOT_REFLEKT_API` to the API project folder: outside a test project the factory does not find the content-root attribute and falls back to `{solution root}\Reflekt.API`, which does not exist. Link the helper files (`<Compile Include="…\Helpers\*.cs" Link=…>`) instead of copying them. With that, two `HubConnection`s over long polling (`HttpMessageHandlerFactory = _ => factory.Server.CreateHandler()`, `AccessTokenProvider` = the guest token) record every SignalR frame two browsers would get. That stood in for the parts of a two-browser walkthrough that need no real sign-in. Evidence: [F38-BackendConventions]
- **An "unused" project reference in a building block can be another project's only path to a dependency.** `Blocks.Persistence` used nothing from `Blocks.Core`, but `Reflekt.API` reached `Blocks.Core` (`Guard`) and, through it, `Blocks.Exceptions` only via `Reflekt.Persistence → Blocks.Persistence → Blocks.Core`; no csproj in the API chain named either. Before removing a reference, grep every downstream project for the removed project's namespaces and add direct references where they are used. Evidence: [F38-BackendConventions]

## Reviewer Lessons

- On this repo every `git diff HEAD` / `git status` call prints a CRLF warning line per changed file (about 160 lines on a restructuring diff), which floods the output. Add `2>/dev/null` to read-only git calls during review.

## Solo Lessons

- **FastEndpoints apps cannot run in parallel in one process.** `MapFastEndpoints` replaces the process-wide `Cfg.SerOpts.Options` with a copy and then changes it (`AddTypedHeaderValueParsers` sets `TypeInfoResolver`). If a request on another host in the same process serializes with the new copy in between, that start-up throws `This JsonSerializerOptions instance is read-only…` and `CreateClient()` fails. The integration suite ran its classes in parallel by xunit's default. The result was a host-start flake in about 2 of 38 integration-only runs here (more often in the complete run), seen in F35, F37 and F38 and never diagnosed because the runner elides the message. `Cfg.ServiceResolver` is static too, so event handlers resolve their services from whichever host mapped last. An integration project with several FastEndpoints hosts needs `[assembly: CollectionBehavior(DisableTestParallelization = true)]`. Evidence: [F38-BackendConventions]
- **To read a test failure the runner elides, set an MSBuild logger through the environment.** Run `VSTestLogger=trx VSTestResultsDirectory={scratch dir} node verify-run.js --role integration …`: `dotnet test` reads both as MSBuild properties and writes a TRX with the full message and stack. The command and the tests stay unchanged. `trx;LogFileName=x` is split at the semicolon and rejected, so pass plain `trx`. Instrumenting the tests themselves (a factory subclass, a first-chance logger) hid this flake for about 100 runs. Evidence: [F38-BackendConventions]
