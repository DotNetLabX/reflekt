## 1. Purpose & Scope

Reflekt is an open-source sprint retrospective tool for .NET teams. V1 is the minimal feature set to run a real retro with Laurentiu's team, nothing more. It is also the live case study for the Claude Code for .NET course shipping June 2026.

**What V1 is:**
- A web app where a small team runs a retro: write cards, vote, discuss, capture action items, generate a report.
- Anonymous participation via a shared room link. No participant accounts.
- First-class evidence linking on cards (GitHub PRs/commits, Jira issues, generic URLs with OpenGraph previews).
- Real-time collaborative UI over SignalR.

**What V1 is NOT (by design, not oversight):**
- A memory layer, agent-authored cards, or the Feedback Flywheel loop — those are v2+, per the strategy doc.
- A Parabol/EasyRetro replacement. V1 ships for one team (Laurentiu's) and doubles as course material.
- A product. It's a feature we use internally. Productization is a later decision gated on real usage signals.

- **Ship Monday.** Weekend build budget. Any feature not essential to running a retro with the team is cut.

- **Practical over complete.** Build features, not a product. If a feature doesn't earn its weekend hours, cut it.

## 3. Identity & Authentication

Reflekt has two identity tiers. Don't blur them.

### 3.1 Team creator — Google-authenticated

- A **Team** is created by a Google-authed user (the Scrum Master, initially Laurentiu).
- Google OAuth 2.0 — email + profile name only. No photo, no extended scopes.
- The team creator is also the **Scrum Master** for all sprints under that team. Roles are not split in v1.
- **Sprint creation is gated to the team creator.** Other Google-authed users cannot create sprints under someone else's team in v1. No invite flow, no multi-admin.

**Why:** V1 serves one team. Team invite flows, role hierarchies, and multi-admin are real features but not weekend-essential. Defer to v2.

### 3.2 Sprint participants — ephemeral guests

- Participants enter a sprint via a shareable **room link**: `/sprint/{sprintId}`.
- On first visit, participant picks a display name. That's the entire onboarding.
- No accounts, no email, no password.
- A `guestToken` (GUID) is generated client-side and stored in `localStorage` under a sprint-scoped key: `reflekt:sprint:{sprintId}:token`.
- On every API call and SignalR connection, the token is sent as a header.
- Backend matches token → `Participant` row. If no match, create a new `Participant` and return the token.
- **Silent rejoin on refresh.** If a matching token is found in localStorage on page load, rejoin as the existing participant without prompting. No "Welcome back, Ana" dialog.
- Switching devices mid-retro = new participant, pick name again. Acceptable tradeoff.

**Why this model (not pure anonymous, not full accounts):**
- Pure anonymous breaks "edit your own cards" — participants can't prove ownership after refresh.
- Full accounts violate the weekend budget and add friction the team doesn't need.
- localStorage guest token is ~1-2h extra work, gives real ownership semantics, and dies cleanly with the session.

### 3.3 Ownership semantics

- Every `Card` and `Vote` references a `ParticipantId`.
- Edit a card: requires `card.ParticipantId == request.ParticipantId` **OR** caller is the Scrum Master.
- Delete a card: requires caller is the **Scrum Master**, OR `card.ParticipantId == request.ParticipantId` (own cards only).
- The Scrum Master can do anything. Participants can only act on their own cards.

## 4. Core Entities

Minimal schema. Extend as needed but don't invent fields we don't use.

```
Team {
  Id: Guid
  Name: string
  CreatorEmail: string        // Google-authed user
  CreatedAt: DateTime
}

Sprint {
  Id: Guid
  TeamId: Guid
  Name: string                // e.g. "Sprint 47"
  State: enum { Draft, Active, Closed }
  CurrentPhase: enum { Writing, Voting, Discussing, Closed }
  VotesPerParticipant: int    // default 3, set at creation
  CreatedAt: DateTime
  ClosedAt: DateTime?
}

Participant {
  Id: Guid
  SprintId: Guid
  DisplayName: string
  GuestToken: string           // GUID, issued to client, stored in localStorage
  JoinedAt: DateTime
}

Card {
  Id: Guid
  SprintId: Guid
  ParticipantId: Guid          // author
  ColumnType: enum { WentWell, DidntGoWell, ActionItems }
  CardType: enum { Note, ActionItem }
  Text: string
  AssigneeName: string?        // nullable; only set when CardType == ActionItem
  CreatedAt: DateTime
  UpdatedAt: DateTime
}

Vote {
  Id: Guid
  CardId: Guid
  ParticipantId: Guid
  CreatedAt: DateTime
}

EvidenceLink {
  Id: Guid
  CardId: Guid
  Url: string
  Source: enum { GitHub, Jira, Generic }
  Title: string?
  Description: string?
  IconUrl: string?
  ImageUrl: string?
  ExternalKey: string?         // e.g. "PROJ-123" for Jira, nullable otherwise
  FetchedAt: DateTime?
  FetchStatus: enum { Pending, Ok, Failed }
}
```

**Notes:**
- `AssigneeName` is a **string copy**, not a foreign key. Action items outlive their assignee participant (who dies with the sprint), and we read the name off the card at retro time. No cross-sprint linking needed.
- Vote-per-card-type constraint (no voting on `ActionItem`) is enforced in the **API layer**, not the schema. Keeps schema simple.
- All foreign keys cascade-delete on `Sprint` removal (not that we delete sprints in v1, but set it up now).

## 5. Retro Mechanics

### 5.1 Columns

**Fixed three-column layout, hardcoded in v1:**
1. **Went well** — `ColumnType.WentWell`
2. **Didn't go well** — `ColumnType.DidntGoWell`
3. **Action items** — `ColumnType.ActionItems`

**Why this template specifically:**
- The third column is already the action-items column, matching the v2 "action items → PRs against CLAUDE.md" pattern. No special casing needed later.
- Not user-configurable in v1. Zero UI cost.

### 5.2 Phases

Sprint has a `CurrentPhase`: `Writing → Voting → Discussing → Closed`.

- Scrum Master advances the phase manually with a button.
- **Phases are soft, not strict.** Participants can technically write cards during Voting, vote during Discussing, etc. Nothing blocks them.
- Current phase is prominently displayed in the UI as context, not enforcement.

**Why soft:** Strict phase enforcement is a UX rabbit hole — "oops Ana is still typing, back to Writing" kills flow in a 30-minute session. Soft phases give the team a shared mental frame without fighting the tool.

### 5.3 Voting

- **Dot voting.** Each participant gets `Sprint.VotesPerParticipant` votes (default 3, configurable at sprint creation).
- Participant can spend votes however they want — all on one card, spread across cards, abstain.
- Real-time: vote counts visible to everyone as they're cast.
- **Anonymous:** cards show count, not who voted.
- **Votes apply to `CardType.Note` only.** Action items are not voted on — you don't vote on a teammate's commitment.
- Participants can retract their own votes (toggle behavior).

### 5.4 Card editing & deletion

- **Edit:** card author OR Scrum Master.
- **Delete:** card author OR Scrum Master.
- Last-write-wins on the rare concurrent-edit case (author + Scrum Master editing simultaneously). No locks, no merge UI.
- If a card is deleted while someone is editing it, their save fails with a toast: "Card was removed."

### 5.5 Card ordering

- **Writing phase:** newest cards first (natural for "I just thought of something").
- **Voting / Discussing phase:** sorted by vote count descending within each column. Discussion flows top-down.
- **Closed phase:** same as Voting/Discussing.

## 6. Evidence Links

The differentiating feature of Reflekt vs Parabol/EasyRetro. Cards can carry Jira / GitHub / generic URL previews.

### 6.1 Supported sources

Auto-detected by URL pattern on paste:

| Source | Detection | Data we fetch |
|---|---|---|
| **GitHub** | `github.com` host | OpenGraph: title, description, image, icon |
| **Jira** | Host matches configured Jira domain, OR URL matches `*/browse/{KEY}` pattern | **Issue key only**, extracted from URL. No API call. |
| **Generic** | Anything else | OpenGraph fallback: title, description, image, icon |

### 6.2 Fetching behavior

- **Async, non-blocking.** On paste: save `EvidenceLink` with `FetchStatus = Pending`, show bare URL immediately, kick off background fetch, push enriched metadata via SignalR when ready.
- **Never block the UI on a fetch.** A slow OpenGraph fetch should not delay card creation.
- **Failure mode:** if fetch fails, set `FetchStatus = Failed`, display bare URL with favicon (if determinable from domain). Don't retry automatically.

### 6.3 Implementation

- **Server-side fetch** using `HttpClient` + `AngleSharp` for HTML parsing. ~30 lines of code. **Do not pull a dedicated OpenGraph library.**
- Timeout: 5 seconds per fetch.
- **SSRF safety:** reject requests to localhost, private IP ranges (10.x, 192.168.x, 172.16.x), and non-HTTP(S) schemes. Basic hostname validation is sufficient — this is for internal team use, not hostile multi-tenant.

### 6.4 Display

- **Inline mode only in v1.** Compact rendering: favicon + title + (for Jira) issue key chip.
- Card mode (full preview box with description and image) is a v2 nice-to-have.
- Clicking a preview opens the URL in a new tab.

## 7. Real-time (SignalR)

### 7.1 Events pushed to all clients in a sprint

| Event | Payload |
|---|---|
| `CardCreated` | Full card object |
| `CardUpdated` | Full card object |
| `CardDeleted` | Card ID |
| `VoteCast` | `{ cardId, newCount }` |
| `VoteRetracted` | `{ cardId, newCount }` |
| `PhaseChanged` | New phase enum value |
| `ParticipantJoined` | Participant object (id, name) |
| `ParticipantLeft` | Participant ID |
| `EvidenceLinkFetched` | Full `EvidenceLink` object with metadata |

### 7.2 Not pushed

- **Card draft text while typing.** Too chatty, no value — retros want finished thoughts, not live typing. Only push on save.

### 7.3 UI behavior

- **Optimistic.** Local action (create, edit, vote) updates the UI immediately, then fires the API call.
- **On API success:** reconcile if the server response differs from the optimistic assumption. Rare.
- **On API failure:** revert the optimistic update, show a toast: "Couldn't save — reconnecting..."

### 7.4 Connection loss & reconnect

- SignalR auto-reconnect is enabled (built-in).
- On reconnect, the client **refetches the full sprint state** (cards, votes, phase, participants). Cheap for a 50-card retro.
- No offline queue, no local-first sync. Overkill for v1.

## 8. Action Items

Action items are cards in the third column with a distinct `CardType` and an assignee.

- `CardType = ActionItem`, `ColumnType = ActionItems`.
- `AssigneeName` is a **string** (the display name of a participant at assignment time), copied onto the card. Not a foreign key — captures the commitment even if the assignee doesn't rejoin future sprints.
- Assignee is chosen from a dropdown of current participants in the sprint when the action item is created or edited.
- **No voting on action items.** Votes table will have zero entries for `CardType.ActionItem`; API rejects vote attempts on action items.
- Action items **can have evidence links** (e.g., "update deployment doc" → link to the doc or relevant PR).

## 9. Sprint Lifecycle

```
Draft ──(SM starts sprint)──▶ Active ──(SM closes sprint)──▶ Closed
```

- **Draft:** Sprint exists, room link not yet shared with team. Optional state — SM may create-and-start in one action.
- **Active:** Room link is live. Participants can join, write cards, vote, etc.
- **Closed:** Read-only. No new cards, no edits, no votes, no phase changes. Report is accessible. Closed sprints stay in the team's sprint list — no archive concept.

**Why closed = strictly read-only:** Matches the "compute report on demand" decision (§10). If closed sprints were editable, the report could drift from the version the team reviewed at close. Making closed sprints immutable means we never need snapshot logic.

SM transitions states manually. No auto-close on phase reaching `Closed`; the phase and the sprint state are independent concepts.

## 10. Report

### 10.1 Endpoint

```
GET /api/teams/{teamId}/sprints/{sprintId}/report
```

Returns JSON. Frontend renders as HTML. Accessible at any time — during an active sprint (useful mid-retro) and after close.

### 10.2 Content

```json
{
  "sprint": { "id", "name", "createdAt", "closedAt" },
  "team": { "id", "name" },
  "participants": [ { "displayName" } ],
  "notes": {
    "wentWell": [ /* cards with ≥1 vote, sorted by voteCount desc */ ],
    "didntGoWell": [ /* same */ ]
  },
  "actionItems": [
    { "text", "assigneeName", "evidenceLinks": [...] }
  ]
}
```

- **Notes:** only cards with **≥1 vote**. Zero-vote notes are dropped from the report.
- **Action items:** all of them, regardless of votes.
- **Evidence links:** embedded on their parent cards.

**What's NOT in the report:**
- Vote counts per card (ordering already conveys importance; showing counts adds noise).
- Card author names (anonymous model).
- Card timestamps.

**Why drop zero-vote notes:** matches "only what's important" — if the team didn't vote on it, it wasn't worth discussing, and certainly not worth revisiting next sprint.

### 10.3 Storage policy

- **Computed on demand, not stored.** No `Report` entity.
- Endpoint is a read view over sprint data with filtering + sorting.
- Closed sprints are read-only (§9), so there's no drift risk.

**Why compute-on-demand over snapshot:**
- Compute cost is trivial — one SQL query with joins, sub-10ms for 50-card retros.
- Snapshotting creates two sources of truth and invalidation logic we don't need.
- Matches Laurentiu's "single source of truth" principle.

### 10.4 Export

- **"Copy as markdown"** button on the report page. Serializes the report to markdown in the clipboard. ~30 lines of code.
- Solves the paste-into-Confluence / paste-into-Slack workflow that every retro-tool user complains about.
- **No PDF export** in v1 (requires a library + layout work, wrong ROI).
- **No CSV export** in v1 (wrong shape for qualitative data).
- **No Jira/Slack push** in v1.

## 12. Open Technical Questions for CC

These are implementation defaults CC should pick sensibly with a one-line reasoning note. Flag any where the "right" answer is genuinely ambiguous.

1. **EF Core migration strategy.** Design-time migrations checked into the repo? Auto-apply on startup in dev?
2. **SQLite file location.** `./data/reflekt.db`? Configurable via `appsettings.json`? Docker volume?
3. **SignalR hub structure.** One hub with groups-per-sprint (cleaner), or one hub per sprint (simpler routing)? Recommend groups.
4. **Google OAuth implementation.** ASP.NET Core `AddGoogle` with cookie auth, or bare OIDC with JWTs? Cookie auth is simpler for a server-rendered landing + SPA-for-sprint model.
5. **Project layout.** See `docs/architecture/v1.md` §4 — four-project split under `src/Services/Reflekt/` (`Reflekt.API / Application / Domain / Persistence`) per CLAUDE.md conventions. Vue app lives in `web/reflekt-web/` and Vite builds into the API's `wwwroot/`.
6. **Google OAuth allowlist for v1.** Allowlist Laurentiu's team's emails only, or allow any Google user to create a team? Recommend: configuration-driven allowlist in `appsettings.json` for v1 — prevents random signups while you're iterating.
7. **Seed data.** Provide a dev-only seed script that creates a test team + one active sprint with 2-3 participants and a handful of cards. Makes local dev and the course demo repeatable.

**Styling:** Use **Tailwind CSS** directly. No Vuetify, no PrimeVue, no full UI kit for v1. shadcn-vue is acceptable if its component coverage matches needs without pulling a heavy runtime. Keep the footprint minimal.

## Decision summary (quick-reference)

| Area | Decision |
|---|---|
| Team creation | Google OAuth, allowlisted emails, one team per creator |
| Participant identity | localStorage guest token, ephemeral per sprint, silent rejoin |
| Ownership | `ParticipantId` on cards/votes; SM has override |
| Columns | Hardcoded: Went well / Didn't go well / Action items |
| Phases | Soft (Writing → Voting → Discussing → Closed), SM advances |
| Voting | Dot voting, 3 votes default, anonymous, notes only |
| Card edit/delete | Own cards + SM override |
| Evidence links | GitHub/Generic via OpenGraph, Jira as URL + issue key chip |
| Evidence display | Inline mode only |
| Real-time | SignalR push on save; optimistic UI; refetch on reconnect |
| Action items | Distinct CardType, AssigneeName as string copy, no voting |
| Sprint lifecycle | Draft → Active → Closed; closed is read-only |
| Report | Computed on demand, markdown copy button, no PDF/CSV |
| Stack | .NET 10 Minimal APIs + MediatR + FluentValidation + Mapster + EF Core + SQLite + SignalR + Vue 3 + TS + Pinia + Tailwind. See `docs/architecture/v1.md`. |
